## Details

### 1. Supabase Edge Functions with `verify_jwt = false`
- Verdict: WORKS
- Finding: With the check on, the platform reads `Authorization` and "expects a valid user JWT. If the header is missing, malformed, or signed with a different key, the platform returns a 401". Turn it off in `config.toml` with `verify_jwt = false`, or pass `--no-verify-jwt`. The docs say to turn it off "for functions that are called without an Authorization header, such as webhooks … or service-to-service calls that authenticate with an API key." An opaque `Authorization: Bearer spx_…` is not a JWT, so it is rejected while the check is on and reaches the function when the check is off. The function must compare the token itself. Supabase publishable/secret keys are a separate case: they are not JWTs, and the docs say to send them on `apikey`, not `Authorization`.
- Build this: Keep `verify_jwt = false` for export, health, push-dispatch, and rest-alarm (E3.5). Accept `Authorization: Bearer spx_…` and check it in the function. Do not rely on the gateway to authenticate that header.
- Sources: https://supabase.com/docs/guides/functions/auth-headers (checked 2026-11-01) · https://supabase.com/docs/guides/functions/function-configuration (checked 2026-11-01)

### 2. Injected env var names, and `SUPABASE_*` secrets
- Verdict: WORKS
- Finding: Injected names include `SUPABASE_URL` and `SUPABASE_SECRET_KEYS` ("The secret keys JSON dictionary"). Legacy `SUPABASE_SERVICE_ROLE_KEY` "still exist[s] in the runtime, but [it] carr[ies] the legacy keys". Read the new one with `JSON.parse(Deno.env.get('SUPABASE_SECRET_KEYS')!)` and use the `default` entry. "A secret name can't start with `SUPABASE_`. That prefix is reserved for the variables Supabase injects, and both the Dashboard and the Management API reject it." The same page documents `supabase secrets set` as the way to set production secrets.
- Build this: Never `supabase secrets set` a `SUPABASE_*` name. Read `SUPABASE_URL` and `SUPABASE_SECRET_KEYS` (`default`). Treat `SUPABASE_SERVICE_ROLE_KEY` as the legacy fallback only. Custom secrets stay `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT`, and `DISPATCH_SECRET` (E3.3).
- Sources: https://supabase.com/docs/guides/functions/secrets (checked 2026-11-01) · https://supabase.com/docs/guides/getting-started/api-keys (checked 2026-11-01)

### 3. Built-in Auth email, and Brevo free with a Gmail sender
- Verdict: PARTIAL
- Finding: Built-in sender: "It sends only to the email addresses of your organization's team members." Other addresses fail with `email_address_not_authorized`. "It sends 2 emails per hour" while confirm-email is on (`over_email_send_rate_limit`). The SMTP guide repeats "2 messages per hour" and "will refuse to deliver messages to addresses that are not part of the project's team." Brevo free: "300 daily email sends" (also "300 email sends per day"). A sender is added under Settings → Senders, Domains, IPs → Senders → Add a sender, then verified with a 6-digit code when the domain is not authenticated. "You are using a free sender domain (such as gmail.com or yahoo.com)." "Note that free sender domains cannot be authenticated, so you'll need to purchase your own domain." "Sending from a free email address (@gmail.com …) will cause your emails to be rejected or filtered to spam." If you do it anyway, "Brevo temporarily replaces your sender address" (example: `mycompany@gmail.com` becomes `mycompany@5000001.t-sender-sib.com` for transactional mail). Brevo does not quote Gmail's DMARC record; it says a Gmail From cannot be authenticated and gets replaced.
- Build this: Custom SMTP is mandatory before inviting a crew member (E3.1). Do not use a `@gmail.com` sender. Use one verified address on a domain you control, with DKIM and DMARC. Brevo free is 300 emails/day. Built-in mail is only a stop-gap to organization members, 2 per hour.
- Sources: https://supabase.com/docs/guides/auth/testing-auth-flows (checked 2026-11-01) · https://supabase.com/docs/guides/auth/auth-smtp (checked 2026-11-01) · https://help.brevo.com/hc/en-us/articles/208589409-About-Brevo-s-pricing-plans (checked 2026-11-01) · https://help.brevo.com/hc/en-us/articles/208836149-Create-a-new-sender-From-name-and-From-email (checked 2026-11-01) · https://help.brevo.com/hc/en-us/articles/14925263522578-Comply-with-Gmail-Yahoo-and-Microsoft-s-requirements-for-email-senders (checked 2026-11-01)

### 4. Email OTP length, expiry, and the first-sign-in template
- Verdict: PARTIAL
- Finding: CLI/config names, which match the Auth server: `auth.email.otp_length` default `6`, "Must be between 6 and 10 digits." `auth.email.otp_expiry` default `3600`, "The expiry time for an OTP code in seconds." Dashboard path found for expiry only: "Authentication > Sign In / Providers > Auth Providers > Email > Email OTP expiration." No current Supabase page quoted a dashboard label "Email OTP Length"; the Management API field is `mailer_otp_length`. 600 seconds is inside the documented expiry (they discourage more than 86,400). The code variable is `{{ .Token }}` ("Contains a 6-digit One-Time-Password"). A local-templates page instead says `Token` "Contains a 8-digit One-Time-Password"; that conflicts with `otp_length` default 6. Hosted projects: "Email confirmation is … on by default." Official Auth source (`magic_link.go`): a missing or unconfirmed user is signed up; if mailer autoconfirm is off, "confirmation email already contains 'magic link'" and only `Signup` runs, which sends `ConfirmationMail` (`mail.SignupVerification`). A confirmed user gets `MagicLinkMail`. So a first `signInWithOtp` on a hosted project gets the Confirm signup template, not Magic Link. Later sign-ins get Magic Link.
- Build this: Put `Your code: {{ .Token }}` in both the Confirm signup and Magic Link templates (E3.2). Set length 6 and expiry 600 seconds. Use `auth.email.otp_length` / `mailer_otp_length` if the dashboard length label is not "Email OTP Length". S2 reads `VITE_OTP_LENGTH` (default 6).
- Sources: https://supabase.com/docs/guides/local-development/cli/config (checked 2026-11-01) · https://supabase.com/docs/guides/auth/auth-email-passwordless (checked 2026-11-01) · https://supabase.com/docs/guides/auth/auth-email-templates (checked 2026-11-01) · https://supabase.com/docs/guides/auth/testing-auth-flows (checked 2026-11-01) · https://github.com/supabase/auth/blob/a7e97d665b9ea03853edb66d014bcde323f7894b/internal/api/magic_link.go (checked 2026-11-01) · https://github.com/supabase/auth/blob/a7e97d665b9ea03853edb66d014bcde323f7894b/internal/api/mail.go (checked 2026-11-01)

### 5. Installed iOS PWA opened from `/join/<CODE>`, and shared `localStorage`
- Verdict: PARTIAL
- Finding: They do not share storage. WebKit: "the website data of home screen web applications is kept isolated from Safari". Bug 181849: "Home Screen apps are created as isolated entities without shared state with the browser." Launch URL: the manifest spec sets `start_url` to the document URL only when the member is missing or not a string; otherwise it parses `start_url` against the manifest URL. On launch with no target URL, "set target URL to start URL." This app's manifest `start_url` is `/?src=pwa`, so the icon opens that URL, not `/join/<CODE>`. WWDC23: "The start_url is the URL that is loaded when the web app is first opened."
- Build this: Do not expect a code saved in Safari `localStorage` to appear in the installed app (E3.8). Show the code large, with Copy, Paste, and typing. Do not rely on the installed app opening at `/join/<CODE>` while `start_url` is set.
- Sources: https://webkit.org/tracking-prevention/ (checked 2026-11-01) · https://bugs.webkit.org/show_bug.cgi?id=181849 (checked 2026-11-01) · https://www.w3.org/TR/appmanifest/ (checked 2026-11-01) · https://developer.apple.com/videos/play/wwdc2023/10120/ (checked 2026-11-01)

### 6. Screen Wake Lock in an installed iOS PWA
- Verdict: WORKS
- Finding: WebKit bug 254545 ("New Wake Lock API does not work in Home Screen Web Apps") is RESOLVED FIXED. It failed in the installed app from iOS 16.4 through 18.3.1. Comment on 2025-03-31: "The Screen Wake Lock API now works in Home Screen Web Apps on iOS and iPadOS 18.4 — which just shipped today." A later iOS 26.1 regression comment was withdrawn the same day (2025-12-04). The muted looping-video fallback is not required on iOS 18.4 or later.
- Build this: Call `navigator.wakeLock.request('screen')` in the installed app and re-request on `visibilitychange`. Keep the silent-video fallback only if the support floor includes iOS older than 18.4.
- Sources: https://bugs.webkit.org/show_bug.cgi?id=254545 (checked 2026-11-01) · https://developer.apple.com/documentation/safari-release-notes/safari-18_4-release-notes#Home-Screen-Web-Apps (cited from that bug; the Apple page returned no extractable body on this check)

### 7. `navigator.storage.persist()` and IndexedDB eviction
- Verdict: PARTIAL
- Finding: `navigator.storage.persist()` returns a promise of whether the user agent will persist the origin. MDN: Safari and most Chromium browsers "automatically approve or deny the request based on the user's history of interaction with the site and do not show any prompts." Firefox shows a prompt. WebKit (2023-08-10): "WebKit currently grants a request based on heuristics like whether the website is opened as a Home Screen Web App." Persistent mode "might be excluded from eviction"; best-effort data can go "when the site has not been interacted with … (see Intelligent Tracking Prevention)." ITP itself: script-writable storage, including IndexedDB and `localStorage`, is deleted "after 7 days of no user interaction" in Safari. "The first-party domain of home screen web applications is exempt from ITP's 7-day cap." Chrome has no 7-day ITP cap; best-effort data can still be evicted under storage pressure, and persistent data is removed when the user clears it.
- Build this: Call `navigator.storage.persist()` once after the first standalone launch and store the boolean in `meta` (Phase 1). Still treat a Safari tab as ephemeral. The durable copy is the installed app, plus the server.
- Sources: https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria (checked 2026-11-01) · https://webkit.org/blog/14403/updates-to-storage-policy/ (checked 2026-11-01) · https://webkit.org/tracking-prevention/ (checked 2026-11-01)

### 9. Free-project pause, and scheduled workflows on a private repo
- Verdict: PARTIAL
- Finding: "Supabase pauses Free Plan projects that show low activity over a 7-day period." Inactive means "it does not receive sufficient user database activity over the past week." "Typically a few user requests to the database each day over the previous week is enough." Listed ways to prevent a warned pause: open the project in the dashboard, or "making API calls to your project." Edge Functions are not mentioned, so a scheduled HTTP ping is not documented as enough unless it causes those database requests. "Paid projects cannot be paused." GitHub: "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days." The same sentence is on the disable-workflow page. Neither page applies that rule to private repositories, and neither defines "repository activity" (including a bot commit).
- Build this: Do not use an Edge Function ping as the only thing that keeps a free project awake (E3.9). Issue a few database requests a day, or use a paid plan. This repo is private, so the 60-day cron disable is not the documented rule. Keep the monthly heartbeat commit only as a guard, as E3.9 already says.
- Sources: https://supabase.com/docs/guides/platform/free-project-pausing (checked 2026-11-01) · https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule (checked 2026-11-01) · https://docs.github.com/en/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows (checked 2026-11-01)

### 11. Cloudflare Pages `_headers`, SPA fallback, preview URLs
- Verdict: WORKS
- Finding: `_headers` is a plain-text file with no extension. A rule is a URL or pattern, then indented `Name: value` lines. "You may define up to 100 header rules. Each line in the `_headers` file has a 2,000 character limit." "If your project does not include a top-level `404.html` file, Pages assumes that you are deploying a single-page application" and "serves the root (`/`) for any incoming path that does not correspond to a static asset." "Every time you open a new pull request on your Git repository, Cloudflare Pages will create a unique preview URL" (only for PRs opened from the same repository). The deployment URL is `<hash>.<project>.pages.dev`. The branch alias is `<branch>.<project>.pages.dev`, lowercased, with non-alphanumeric characters replaced by a hyphen (`fix/api` → `fix-api.<project>.pages.dev`).
- Build this: Ship `public/_headers` (generated into `dist/_headers` per E3.6). Do not add a top-level `404.html` if client-side routes must fall through to `index.html`. Preview URLs are per deployment hash plus a branch alias. A8 can rely on this.
- Sources: https://developers.cloudflare.com/pages/configuration/headers/ (checked 2026-11-01) · https://developers.cloudflare.com/pages/platform/limits/ (checked 2026-11-01) · https://developers.cloudflare.com/pages/configuration/serving-pages/ (checked 2026-11-01) · https://developers.cloudflare.com/pages/configuration/preview-deployments/ (checked 2026-11-01)

### 12. Web Push on iOS, and `npm:web-push` on Supabase Deno
- Verdict: PARTIAL
- Finding: Apple: "Add web push to Home Screen web apps in iOS 16.4 or later." "Provide a method for the user to grant permission with a gesture … call the push subscription method immediately from the gesture's event handler." "Safari doesn't support invisible push notifications. Present push notifications to the user immediately after your service worker receives them. If you don't, Safari revokes the push notification permission for your site." WWDC23: Web Push on iOS needs `display` `standalone`. `web-push` on npm is `3.6.7` (published 2024-01-16). Its issue 718 quotes `crypto.createECDH('prime256v1')` and a non-Node runtime throwing `crypto2.createECDH is not a function`. No Supabase doc says `npm:web-push` runs in Edge Functions. `jsr:@negrel/webpush@0.5.0` is "Web Push library for Deno and other web compatible runtime" and "works with … Deno", using SubtleCrypto. The JSR page says "Published a year ago" and does not show an ISO date.
- Build this: Phase 7 push is installed-PWA only, iOS 16.4+, permission from a tap, and every push calls `showNotification`. Do not import `npm:web-push` in an Edge Function. Use `jsr:@negrel/webpush@0.5.0`. A live send from Supabase is still unproven.
- Sources: https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers (checked 2026-11-01) · https://developer.apple.com/videos/play/wwdc2023/10120/ (checked 2026-11-01) · https://www.npmjs.com/package/web-push (checked 2026-11-01) · https://github.com/web-push-libs/web-push/issues/718 (checked 2026-11-01) · https://jsr.io/@negrel/webpush (checked 2026-11-01)
