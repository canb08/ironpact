## Scope
1. `src/data/db.ts`: Dexie database **`ironpact`** (§10 E1.1), stores per §4.6 (+ `outbox`, `meta`). Mirror rows exactly as `types.ts`.
2. `src/data/ids.ts`: `newId()` = `crypto.randomUUID()`; `bodyweightId(userId, localDate)` = uuidv5 with a fixed `NS_BODYWEIGHT` constant.
3. `src/data/clock.ts`: injected clock; per-launch offset `server_now − (t0 + rtt/2)` always applied (E5.4); `localDateIn(tz, instant)` via `@date-fns/tz`.
4. `src/data/outbox.ts`: one Dexie rw transaction = mirror upsert + outbox entry; **coalesce** pending entries per `[table+row_id]`; `isPending(rowId)`.
5. `src/data/sync.ts`: single-flight flush; triggers (start, `online`, `visibilitychange→visible`, every 30 s visible, after write when online); table priority order (`SYNCED_TABLES`); batches ≤100; **E5.1** write returned rows back / fetch missing ids; **E5.2** 4xx → bisect to the single bad row → `dead` with `last_error`; backoff 2→4→8→16→32→60 s on transient; `server_asleep` after 3 consecutive transient failures; status stream (`SyncStatus`).
6. `src/data/pull.ts`: **E5.3** keyset pagination on `(updated_at, id)` with 5 s overlap, pages of 1000; never overwrite a row with a pending outbox entry; per-table cursor in `meta`.
7. `src/data/repo.ts`: implements `Repo` on top of the above for **any** `Remote`. Validation via zod schemas in `src/core/validate.ts` is Codex B's ticket B2 — until it lands, call a local `validate*` shim inside `src/data/` that you delete when B2 merges (note it in the PR). `local_date` per E5.5 (session tz = device tz at start; children copy the session's date). Floor MIN = 1 call → `kind='min'` session + `min_entries` row in one transaction. Bodyweight same-day replace via `bodyweightId`. `softDelete` of a set also soft-deletes its `pr_events` in the same outbox batch.
8. `src/data/adapter.mock.ts`: in-memory `Remote` with the **same semantics as the DB** that matter to sync: LWW on `client_updated_at` (equal → apply), server-set `updated_at`, `user_id` ownership rejection (4xx), invite/token RPCs, two seeded users (`alice@example.test`, `bob@example.test`; any 6-digit code works in mock) already in one crew, plus a `simulateCrewmateActivity()` helper for demos and e2e. Optional `latencyMs` and `failNext(n, kind)` hooks for tests.
9. `src/data/index.ts`: `createRepo()` picks the Remote from `VITE_BACKEND` (`mock` | `supabase`); the Supabase Remote is ticket A7 — until then `supabase` throws "A7 not merged" (don't stub it as working).
10. **Contract test suite** `tests/unit/data/repo.contract.ts`: a function `runRepoContract(makeRemote)` that A7 will also run against Supabase. Run it here against the mock (`fake-indexeddb`). Must include:
    - log 20 sets offline → go online → flush → exactly 20 server rows, 0 duplicates; same outbox item sent twice → 1 row; kill mid-flush (abort after first batch) → reopen → still exactly 20;
    - 5 edits of one set → 1 upsert (coalescing);
    - LWW: older `client_updated_at` loses, device converges to server value (E5.1);
    - one invalid row in a batch of 100 → 99 synced, 1 dead, queue not blocked (E5.2);
    - pull keyset with many rows sharing one `updated_at` → none skipped (E5.3);
    - session at 23:30 on Sun 25 Oct 2026 Europe/Amsterdam (DST end) + set at 00:10 → both `local_date` 2026-10-25;
    - bodyweight twice in a day → one row, later value;
    - pending local edit is not overwritten by a pull;
    - soft-deleting a set soft-deletes its PR events in the same batch.
